## 2. Codex용 전체 문장 프롬프트

```text
You are a senior frontend engineering agent working on a maintainable production-style prototype.

I want you to upgrade an existing legacy single-file HTML tool called PCB Panel Yield Visualizer into an operational frontend SPA using Option B architecture.

Use the following stack exactly unless there is a strong technical reason to improve it while keeping the same architectural direction: React, TypeScript, Vite, Tailwind CSS, Zustand, Vitest, and Playwright.

Your goal is not to create a quick demo. Your goal is to produce a clean, extensible, and runnable codebase that preserves the core behavior of the legacy app while making the structure suitable for future feature growth.

The product must preserve these core behaviors from the legacy HTML app. The user must be able to choose a panel preset or enter a custom panel width and height. The user must be able to enter product width and height, border loss, gap, and rotate mode. The app must calculate total quantity, yield, array layout, and remaining width and height in real time. The app must display optimization guidance for width and height adjustment thresholds. The app must render the panel layout visually using canvas. The app must support zoom, pan, and PNG export.

The upgraded product must also add these requirements. The default theme must be Light mode. The app must support Light mode, Dark mode, and Blue-Gray mode. The selected theme and latest input configuration must persist through localStorage. The app must show validation messages for invalid, impossible, or unrealistic inputs. The UI must be responsive and remain usable on desktop first, while also behaving reasonably on tablet and mobile sizes.

Use this target UI structure. The header must contain the app title, a theme switcher, a help action placeholder, and a PNG export action. The left panel must contain configuration inputs, an advanced process options placeholder, result summary cards, optimization guide cards, preset and history placeholders, and a legend. The right panel must contain a canvas toolbar, the main canvas viewport, and a status bar.

Use the following architecture rules. Separate presentation, state, domain logic, rendering, validation, persistence, and export concerns. Keep calculation logic in pure functions. Keep canvas rendering in a dedicated renderer module. Do not hide business logic inside JSX. Do not create one giant component. Use Zustand stores with minimal subscriptions. Use theme tokens or CSS variables for theme management. Structure the code so that presets, history, comparison mode, process rules, and manual placement mode can be added later without major rewrites.

Create a project structure that includes layout components, form components, result components, guide components, canvas components, feature modules for yield calculation, validation, theme, and persistence, store modules, export services, shared utilities, tests, and a README.

Implement the first working version completely. Do not leave pseudocode. Do not skip wiring between files. Do not leave disconnected components. Add sample unit tests for the core calculation functions. Add at least one Playwright smoke test that verifies app load and theme switching. Make sure the app installs, runs, and builds successfully.

Work in this order. First, inspect the problem and produce a short implementation plan. Second, scaffold the project structure. Third, implement the domain calculation layer. Fourth, implement the stores and theme system. Fifth, implement the UI layout and forms. Sixth, implement the canvas renderer and toolbar interactions. Seventh, implement persistence and export. Eighth, add tests. Ninth, add a clear README with setup and run instructions. Tenth, summarize what was completed, what remains as placeholders, and how the legacy logic was mapped into the new architecture.

Prefer clean engineering decisions over flashy UI. Keep the design practical, professional, and suitable for an engineering dashboard. Preserve the original app behavior wherever the old logic is clear. Where the legacy behavior is ambiguous, choose the safest interpretation and document it in comments or the README.
```

## 3. Claude Code용 전체 문장 프롬프트

```text
You are my senior frontend pair programmer and codebase-aware implementation assistant.

I am upgrading a legacy single-file HTML application called PCB Panel Yield Visualizer into an operational React SPA based on Option B architecture. I want you to work like an experienced engineer who can read a codebase, plan the refactor, implement the new structure, run checks, and improve the result in a maintainable way.

Use this stack for the implementation: React, TypeScript, Vite, Tailwind CSS, Zustand, Vitest, and Playwright.

You must preserve the important product behaviors from the legacy version. The app must allow panel preset selection and custom panel size input. The app must allow product width and height input, border loss input, gap input, and rotate mode selection. The app must calculate quantity, yield, layout array, and remaining width and height in real time. The app must show optimization guidance for width and height adjustments. The app must render the board arrangement using canvas. The app must support zoom, pan, and PNG export.

You must also add operational product structure. The default theme must be Light mode. The app must support Light, Dark, and Blue-Gray themes. The current theme and latest user configuration must be saved in localStorage. The app must display validation messages and invalid-state UI when input values are impossible or out of range. The generated codebase must be easy to extend later for presets, history, comparison mode, process options, and manual placement mode.

Build the app using a clear architecture. Separate components for layout, forms, results, guides, and canvas. Separate feature modules for yield calculation, validation, theme, and persistence. Separate stores for app state, theme state, and history or preset state if needed. Separate services for export behavior. Keep the calculation logic in pure functions and keep the canvas drawing logic in a dedicated renderer module. Avoid putting business logic directly inside JSX.

Use this UI structure. The header should include the app title, theme switcher, help placeholder, and PNG export action. The left panel should include the configuration form, advanced process options placeholder, result summary, optimization guide, preset and history placeholders, and legend. The right panel should include a canvas toolbar, a main canvas viewport, and a status bar.

I want you to work in this output order. First, inspect the task and write a concise implementation plan. Second, show the proposed folder structure. Third, implement the app. Fourth, add tests. Fifth, add a README. Sixth, provide a short gap list for the next iteration.

Use strong TypeScript typing. Create a reusable theme token system. Add at least one or two sample validation rules. Add at least one or two sample unit tests for core calculation logic. Add one Playwright smoke test for app load and theme switching. Make sure the app runs without manual patching.

As you work, favor clarity over cleverness. Keep the interface practical and engineering-dashboard oriented. Do not generate placeholders unless they are explicitly labeled as placeholders. Keep the code ready for the next round of improvements.

When you are done, provide a summary of implemented files, the install and run commands, the remaining gaps, and the next recommended refactor steps.
```

## 4. Antigravity용 전체 문장 프롬프트

```text
Mission: Upgrade a legacy single-file HTML engineering tool called PCB Panel Yield Visualizer into an operational frontend SPA using an agent-first development workflow and Option B architecture.

Your mission is to produce a modern, maintainable, and runnable React application that preserves the core calculation behavior of the legacy app while significantly improving maintainability, performance readiness, stability, and extensibility.

The required stack is React, TypeScript, Vite, Tailwind CSS, Zustand, Vitest, and Playwright.

The product must preserve the following existing behaviors. It must support panel preset selection and custom panel dimensions. It must support product width and height input, border loss input, gap input, and rotate mode selection. It must calculate total quantity, yield, layout array, and remaining width and height in real time. It must show optimization guidance for width and height adjustment thresholds. It must render the panel layout in a canvas-based visualization. It must support zoom, pan, and PNG export.

The product must also add the following operational requirements. The default theme must be Light mode. The available themes must be Light, Dark, and Blue-Gray. The latest user configuration and selected theme must persist in localStorage. The app must provide validation feedback for invalid or impossible inputs. The structure must be prepared for future presets, history, comparison mode, process rule expansion, and manual placement mode.

The system design must include a presentation layer, a state layer, a domain calculation layer, a canvas rendering layer, and a persistence layer. Business logic must remain outside of UI components. Canvas drawing must be handled by a dedicated renderer module. Theme handling must use tokens or CSS variables. State subscriptions must be kept minimal. The codebase must be modular and ready for future extension.

Use the following target UI layout. The header must include the app title, theme switcher, help action placeholder, and export action. The left control panel must include the configuration form, advanced process options placeholder, result summary cards, optimization guide cards, preset and history placeholders, and legend. The right visualization panel must include a canvas toolbar, the main canvas viewport, and a status bar.

Use the following task decomposition as a working plan. One workstream should scaffold the Vite, React, and TypeScript application with all core dependencies. One workstream should implement the theme system with Light mode as default and with Dark and Blue-Gray alternatives. One workstream should implement the domain calculation functions and validation helpers. One workstream should implement the layout components and the left and right panel structure. One workstream should implement the canvas renderer, zoom, pan, and PNG export. One workstream should implement persistence for theme and latest configuration. One workstream should add Vitest unit tests and a Playwright smoke test. One workstream should review architecture quality and identify extensibility gaps.

Execute the mission in a disciplined order. Start with a short mission plan. Then scaffold the project. Then implement the domain layer. Then implement state and theme management. Then implement the UI layout. Then implement canvas behavior. Then implement persistence and export. Then add tests. Then add a README with setup and run instructions. Then provide a final report.

Definition of done: the app runs successfully, the major legacy behaviors are implemented, Light mode is the default theme, theme switching works, yield calculation works, the canvas renders, PNG export works, sample tests pass, and the README is included.

Final report format: completed tasks, open gaps, architecture notes, run commands, and recommended next milestone.
```

## 5. 사용 팁

### Codex에 넣을 때
- 한 번에 큰 구조 생성이 필요할 때 적합하다.
- 멀티파일 프로젝트 생성과 테스트까지 한 번에 밀어붙이기 좋다.

### Claude Code에 넣을 때
- 기존 코드베이스를 이해시키면서 단계적으로 리팩터링하고 싶을 때 적합하다.
- 계획, 구현, 검토, 리팩터링 흐름이 자연스럽다.

### Antigravity에 넣을 때
- 작업을 미션 단위로 분해하고 여러 에이전트 흐름으로 병렬 실행하고 싶을 때 적합하다.
- 구조 리뷰와 역할 분담형 개발에 강하다.
